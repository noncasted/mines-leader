# Идеи по клиенту

Список «на подумать». Не задачи, а направления, которые меняют способ письма кода.

## 1. Структурная конкурентность вместо `.Forget()`

В игровом коде ~40 `.Forget()`. Каждый такой вызов это задача без владельца: исключение
уходит в никуда, завершения никто не ждёт. Так молча умирает `GameLoop`.

Идея из Kotlin coroutine scopes и Trio: задача обязана принадлежать скоупу.
`lifetime.Launch(task)` вместо `Forget`, `ILoadedScope.Dispose` ждёт всех запущенных,
необработанное исключение ребёнка завершает скоуп. Асинхронный код становится деревом
с корнем в `Startup`, а не набором выстрелов.

Не массовая вещь, но закрывает целый класс ошибок и дешёвая: лайфтайм и точка ожидания
уже есть.

## 2. Запись и воспроизведение матча

Игра пошаговая, весь вход клиента это MemoryPack-сообщения от сервера и действия игрока.
Если писать их в файл с таймингами, любой баг становится воспроизводимым файлом.
Дальше это же даёт time-travel: скрабить состояние реактивных свойств в редакторе.

Половина уже есть: `AgentMatchFixture` подкладывает состояние перед стартом,
`ProfilerTraceStorage` пишет трассы на диск, недетерминизма в Shared три файла.
Цена: единственная точка входа для случайности и времени.

Багрепорт = реплей, тест = реплей + ассерт.

## 3. Типизированная иерархия из префабов

### Проблема

В клиенте ~400 `[SerializeField]`. Каждое поле это ручное связывание перетаскиванием
и ошибка, которая проявляется только в рантайме как null. Переименование объекта
в иерархии ничего не ломает на этапе сборки, а ломает в билде. Каталог ассетов эту
проблему решил на уровне «какие префабы есть», но не на уровне «что внутри префаба».

### Идея

Тот же ход, что каталог ассетов, но на уровень ниже. Аналог Android ViewBinding:
генератор проходит по префабу и выдаёт partial-класс с типизированными свойствами
по именам детей. Сам класс пишет логику, партиал держит связывание.

```csharp
// GamePauseSettings.cs, пишется руками
public partial class GamePauseSettings : MonoBehaviour, IGamePauseSettings, ISceneService
{
    public void Create(IScopeBuilder builder)
    {
        MasterVolume.ToLifetimedValue(lifetime).View(...);
        BackButton.ListenClick(lifetime, ...);
    }
}

// GamePauseSettings.Bindings.g.cs, генерируется
public partial class GamePauseSettings
{
    [SerializeField, HideInInspector] private Object[] _bindings;

    private Slider MasterVolume => (Slider)_bindings[0];
    private Slider MusicVolume => (Slider)_bindings[1];
    private GamePauseSettingsSwitch VSync => (GamePauseSettingsSwitch)_bindings[2];
    private Button BackButton => (Button)_bindings[3];
}
```

### Как связывать в рантайме

Без поиска и без рефлексии. Генератор при прогоне сам заполняет скрытый массив
`_bindings` ссылками на компоненты и помечает префаб dirty, как `PrefabCatalogGenerator`
пишет группы. Unity сериализует ссылки штатно, в рантайме это индекс в массив.
Путь в иерархии хранится только в метаданных генератора для ремонта.

Поиск по пути через `transform.Find` в `Awake` не нужен: он стоит времени и ломается
при перемещении объекта.

### Что помечать и как

Не всю иерархию: только объекты, которые нужны коду. Маркер на объекте в иерархии,
по аналогии с галочкой «Included» у каталогов. Варианты:

- компонент-маркер `Bind` на объекте с полем «имя свойства» (по умолчанию имя объекта)
  и стабильным GUID;
- соглашение по имени, например префикс `@` у объекта.

Компонент-маркер лучше: в нём живёт GUID, и переименование объекта превращается
в переименование свойства, а не в потерю ссылки. Генератор видит старый GUID с новым
именем и просто перегенерирует. Ровно так `PrefabCatalogMetadata` чинит ссылки
при переименовании типов.

### Откуда тип

Из компонентов на помеченном объекте:

- один компонент кроме `Transform` — он и есть тип;
- несколько — явный выбор в маркере, иначе ошибка генерации;
- ни одного — `GameObject` или `RectTransform`.

Если у ребёнка свой класс с биндингами, свойство типизируется им и внутрь генератор
не заходит. Это граница вьюхи: `GamePauseSettings` видит `VSync` как
`GamePauseSettingsSwitch`, а не его слайдеры.

### Списки

Несколько детей с одним именем и числовым суффиксом (`Slot_1 … Slot_N`) дают
`IReadOnlyList<SlotView>`. Только статические наборы. Динамические списки это
`ViewableList`, генератор их не трогает.

### Проверки на этапе генерации

- дубликат имени свойства в одном классе;
- маркер без подходящего компонента нужного типа;
- маркер ссылается на объект вне своего префаба;
- имя не является идентификатором C# (правила `CatalogNaming`).

Переименование объекта без обновления кода даёт ошибку компиляции в месте использования,
а не пустую ссылку в билде.

### Что уже есть в стеке

- `ScopeEntityView.OnValidate` уже сканирует детей по интерфейсу, это прототип обхода;
- `PrefabCatalogGenerator` ходит по префабам, знает их сборку и умеет чинить ссылки;
- `CatalogGenerationRunner` даёт дебаунс и защиту от прогона во время компиляции;
- `GeneratedFile.WriteIfChanged` не трогает файл без изменений;
- маршрутизация по asmdef кладёт генерат рядом с классом в `Generated` его сборки.

### Открытые вопросы

- варианты префабов и вложенные префабы: наследовать биндинги базового или
  генерировать заново;
- сцены сервисов: те же правила через сканер сцен из `ScenesCatalog` или отдельно;
- ссылки на ассеты, а не на детей (спрайты, конфиги): это уже каталог ассетов,
  генератор биндингов их не касается;
- Odin-кнопка «Rebind» на компоненте против автоматического прогона на импорт префаба.

### Миграция

Класс за классом. Старые `[SerializeField]` продолжают работать, партиал добавляется
рядом. Первые кандидаты: экраны UI с шестью и больше полями.

### Ожидаемый эффект

Минус большинство ручных полей, ошибки привязки на генерации, рефакторинг иерархий
без страха. Плюс исчезает класс багов «после мержа ссылка слетела», потому что
источник правды это маркер с GUID, а не позиция в инспекторе.
