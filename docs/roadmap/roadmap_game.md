# Game — Roadmap

Связанная цепочка задач: перевод игрового цикла на ручное управление снапшотами, что открывает
возможность воспроизведения прошлых матчей, наблюдения за текущими (spectator) и реализации турниров.
Каждая следующая задача опирается на предыдущую.

---

## 1. Полный переход на мануальные снапшоты

**Что:** Убрать автоматическую подписку снапшотов на события грейна:

```csharp
snapshot.HandleBoards(lifetime, _gameContext);
snapshot.HandlePlayers(lifetime, _gameContext);
```

Все команды (`OpenCellCommand`, `CardUseCommand`, `SetFlagAction`, `CheatCommands`, `BotCommandUtils`
и раунды `TimeLimitedRound` / `LastManStandingRound`) должны формировать снапшот явно —
через явный вызов `Snapshot.Capture*()` в нужные моменты.

**Зачем:** Автоматическая подписка связывает снапшот с временем жизни команды и делает поведение
недетерминированным — то, что попадает в снапшот, зависит от порядка событий и lifetime'ов.
Ручной контроль позволяет:
- Знать точный момент каждого снапшота (для реплея).
- Гарантировать одинаковое содержимое снапшота между live-игрой и восстановлением.
- Упростить отладку: снапшот = результат явного действия, а не побочный эффект.

**Затрагивает:**
- `backend/Game/GamePlay/Context/MoveSnapshot.cs` — API без `HandleBoards`/`HandlePlayers`
- `backend/Game/GamePlay/Commands/*` — все команды
- `backend/Game/GamePlay/Context/Rounds/*` — раунды
- `backend/Game/GamePlay/Bot/BotCommandUtils.cs` — боты

**Блокирует:** задачи 2, 3, 4.

## 2. Реплей прошлых матчей

**Что:** Сохранять последовательность снапшотов матча в долговременное хранилище и давать клиенту
восстанавливать состояние на любой момент времени.

**Модель данных:**
- `MatchReplay` — метаданные матча (id, участники, длительность, результат).
- `ReplayFrame[]` — упорядоченный список снапшотов с временной меткой и привязкой к действию
  (команда / событие раунда), породившему снапшот.

**UI/UX:**
- В истории матчей (match history screen) — кнопка «Просмотреть».
- Плеер с шкалой времени: play / pause / скраббинг / скорость.
- Клиент перестраивает доску и состояние игроков из снапшота без пересчёта команд.

**Зачем:** Даёт игрокам анализировать свои и чужие матчи, аналитикам — материал для баланса карт,
QA — воспроизведение багов по id матча.

**Зависит от:** 1 (снапшоты должны быть детерминированными и полными).

**Затрагивает:**
- `shared/` — протокол `ReplayFrame`, `MatchReplay`.
- `backend/Game/` — запись снапшотов, grain/сервис для выдачи реплея.
- `backend/Meta/` — индексация и поиск по матчам.
- `client/` — плеер реплея.

## 3. Спектатор живых матчей

**Что:** Возможность присоединяться к идущему матчу в режиме наблюдателя и видеть то же состояние,
что и игроки (или с задержкой против читеров).

**Механизм:** Использует тот же поток снапшотов, что и реплей, но в live-режиме:
- Grain матча пушит каждый новый снапшот подписчикам через messaging.
- Клиент-спектатор получает снапшоты и воспроизводит их как в реплее, но без скраббинга вперёд.
- Присоединение в середине матча = загрузить последний снапшот + подписаться на дельты.

**UI/UX:**
- Список идущих публичных матчей.
- Кнопка «Смотреть» — вход в тот же игровой экран, но с заблокированным вводом.
- Переключение между игроками, общий вид.

**Зачем:** Социальный пласт (смотреть за друзьями, стримы, киберспорт), а также — обязательное
условие турнирных трансляций.

**Зависит от:** 1 (ручные снапшоты), 2 (формат `ReplayFrame` и плеер на клиенте).

**Затрагивает:**
- `backend/Game/` — подписка на снапшоты активного матча.
- `shared/` — протокол спектатора.
- `client/` — режим просмотра live-матча, UI списка матчей.

## 4. Турниры

**Что:** Полноценный турнирный режим поверх всей предыдущей инфраструктуры.

**Компоненты:**
- **Турнирная таблица** — сетка (single/double elimination, swiss, round-robin), синхронизируется
  через стейт-систему и отображается всем участникам и зрителям.
- **Автопереход между матчами** — по завершении матча игроки автоматически попадают в следующий
  по сетке; очередь, готовность, таймауты.
- **Спектаторы матчей турнира** — любая пара / матч турнира открыт для просмотра через механизм из 3.
- **Проекция таблицы в матч** — во время матча игроки и зрители видят актуальное состояние сетки
  (следующие соперники, выбывшие, текущие счёта).

**Зачем:** Превращает игру из набора одиночных матчей в событие с целью — повышает вовлечённость,
ретенцию и соревновательность.

**Зависит от:** 1, 2, 3.

**Затрагивает:**
- `backend/Meta/` — турнирный грейн, сетка, расписание, посев, результаты.
- `backend/Game/` — связывание матчей с турниром, передача результатов.
- `shared/` — протокол турниров.
- `client/` — UI таблицы, лобби турнира, оверлей проекции в матче, интеграция спектатора.

## 5. Превью карт в меню (изолированный визуал)

**Что:** При наведении на карточку в меню (коллекция, колода, магазин, описание) показывать
анимированный превью того, как карта работает на реальной доске: эффект разыгрывания,
затронутые клетки, анимация карт-персонажей, звуки — всё как в матче, но в мини-окне.

**Почему это большая задача:** Визуализация карты в матче завязана на полный контекст —
`IGameContext`, `MoveSnapshot`, `IBoard`, состояние игроков, messaging, транзакции, стейт.
Чтобы отрисовать превью в меню, нужно весь этот стек запустить в изолированном контейнере
без реального матча.

**Требуется:**
- **Моки backend-сервисов на клиенте:** fake `IGameContext`, fake `IBoard`, fake players,
  fake messaging — достаточно полные, чтобы `ICard.Execute` / команды отработали и породили
  визуальные эффекты.
- **Изолированный DI-скоуп:** отдельный VContainer-контейнер под превью, чтобы моки
  не утекали в настоящий gameplay-скоуп.
- **Детерминированная мини-доска:** преднастроенный board state под каждую карту —
  показательный сценарий, демонстрирующий эффект.
- **Обход реального ввода/сети:** превью прокручивается по таймеру, без транзакций и сетевых вызовов.
- **Lifetime-контроль:** превью создаётся и уничтожается с hover'ом — все подписки должны
  корректно терминироваться, иначе — утечки при частом наведении.
- **Переиспользование визуальной части карт:** view-слой карт не должен знать, live это матч
  или preview — только данные состояния. Потребует рефакторинга текущих view-компонентов,
  если они тянут сервисы напрямую.

**Зачем:** Игроки понимают, что делает карта, до покупки/сборки колоды. Снижает порог входа,
уменьшает количество бесполезных сборок, усиливает восприятие арта и анимаций.

**Не зависит от 1–4**, но может переиспользовать инфраструктуру реплея (п. 2): «превью» —
это, по сути, проигрывание заранее записанного снапшота сценария карты.

**Затрагивает:**
- `client/` — новый preview-скоуп, моки игровых сервисов, UI hover-попапа, рефакторинг
  view-слоя карт для работы без реального gameplay-контекста.
- `shared/` — возможно, формат «сценарий карты» (board + действия), если использовать
  снапшот-инфраструктуру.
- Арт: подготовка показательных board-сценариев под каждую карту.
