Durable transactions
Instead of direct writing to db, during Commit phase, actors return their state with Prepare method and then 
transaction commiter writes to db under single transaction.

Grain placement
Each grain has PlacementIdentity which points to the silo, where grain should deploy.
All PlacementIdentities are stored in IdentityCache, which is calculating each time when project starts,
new silo is connected, or disconnected.
Local placement is always preferred, so when we want to deploy a grain in silo different from PlacementIdentity,
we should go to this silo and write PlacementAcquirement, so all new silos will know where grain is deployed.
When grain is disposed we should free PlacementAcquirement on related silo.

State identity
For state identity GrainKey should be used as a key, for example: 
int for IGrainWithIntegerKey
string for IGrainWithStringKey
and so on

Collections
There should be no global collection in a singleton grain, like PlayersCollection.
Instead there should be a dedicated db table, where all entities are stored and CollectionView which represents 
this table and provides all operations with it. It may even cache all entities and load them during startup.

State versioning
Each state should have property Version which is incremented each time when state is changed. 
Every time state is changed its copy with version postfix State_v{Version}.cs and corresponding migration should be created.
Then, during state read we check state version from db, and apply each migration until we get the latest version of state.
During state write, we should write new version in db.
