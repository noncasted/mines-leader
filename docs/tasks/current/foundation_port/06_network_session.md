# 06. Сеть, сессии, протокол (N1-N13)

A = `/projects/peace-data-reborn`, B = этот репозиторий. Пути без префикса указаны в B от `backend/`. Клиентская сеть: `client/Assets/Common/Internal/Runtime/Network` (сокращение **Cn**; при расхождении путь искать `grep`-ом).

Сверка проведена 2026-10-20. Сравнивались B, A на старте этапа (`0a67a0b08^`) и дифф каждого коммита. В B нет и нескольких исправлений, которые A сделал ещё **до** этапа: `f7ce94d17` (чтение сообщения websocket целиком), `91540c288` (keep-alive и закрытие сессии), `ConcurrentDictionary` в `SessionsCollection`.

N4, N6, N7 меняют протокол. Выкатывать их одним релизом вместе с S3 и S4 (overview, "Протокольный релиз").

## N1. Backend: чтение и запись websocket

- **Приоритет:** P0, отказ в обслуживании и порча данных. **Волна:** 1.
- **Источник в A:**
  - `f7ce94d17`: `WebSocketMessageReader`, чтение сообщения целиком с лимитом размера;
  - `c42ea344f` (F2.4): `Common/Network/ConnectionWriter.cs`, тест `Tools/Tests/Network/ConnectionWriterTests.cs`;
  - `3bdde2d39`: тест `Network/ConnectionReaderTests.cs`.
- **Проблема:**
  - `Common/Network/ConnectionReader.cs:40,48,74` и `ConnectionOneTimeHandle.cs:18`: буфер 4 МБ на каждый сокет и на каждый handshake, поэтому память легко исчерпать. `EndOfMessage` игнорируется, и сообщение из нескольких кадров портится.
  - `Common/Network/ConnectionWriter.cs:79`: `buffer.Position = 0` стоит не в `finally`. После ошибки отправки следующее сообщение уходит с мусором в начале.
  - `ConnectionWriter.cs:34,36-43,96,130,156`:
    - запросы хранятся в обычном `Dictionary`;
    - `_requestId++` не атомарен;
    - `SetResult` без `TrySet`;
    - нет `Complete` в `finally`;
    - `Bounded(10)` с `Wait` без токена: продюсеры зависают на полном канале.
- **Шаги:** `ConnectionWriter` в B совпадает с A на старте этапа, поэтому reader и writer из A берутся целиком вместе с `WebSocketMessageReader`; тесты переносятся.
- **Готово:** тесты зелёные; сообщение больше лимита закрывает сокет; многокадровое сообщение собирается.

## N6. Union-теги явно

- **Приоритет:** P1, тихая порча данных при изменении порядка типов. **Волна:** протокольный релиз.
- **Источник в A:** `d4ccc67b2`, `6ceb82b0e` (F3.1): явные теги рядом с типами, диапазоны тегов, одна регистрация; golden-тест байтов `3bdde2d39` (`Tools/Tests/Protocol/ProtocolBytesTests.cs`, `protocol_bytes.golden.txt`, клиентский `ProtocolBytesTests.cs`).
- **Проблема:** `shared/Protocol/UnionBuilder.cs:27-28` выдаёт теги по порядку регистрации. Вставка или перестановка типа незаметно сдвигает теги, и старый клиент разбирает не тот тип.
- **Шаги:**
  1. Golden-тест байтов **до** правки на текущем протоколе B.
  2. Явные теги, сохраняющие текущие значения.
  3. Golden-тест не меняется.
- **Готово:** golden-тест зелёный до и после; добавление типа без тега падает при старте или в тесте.
