# N11. Сущности: буфер создания, уничтоженные id, диапазоны id — handoff

Статус: **не подтверждено** (все три пункта). Код не менялся.
Источник: peace-data-reborn `742f8168f` (F2.18-F2.21). Объём по решению оркестратора: диапазон id, буфер создания, список уничтоженных id. Батч записи свойств не переносится.

## Шаг 0: как B использует слой сущностей

Проверено чтением кода в worktree после ff на main (там уже N8 и N9):

- В B есть только одна сущность — игрок, и создаёт её **сервер**: `GameFlow` → `PlayerFactory.Create` → `EntityBuilder.Build` → `SendAll(CreatedOverview)`. На пользователя за матч — одна сущность.
- Сетевых свойств у сущностей нет ни на сервере (у `EntityBuilder.AddProperty`/`WithProperty` нет вызовов), ни на клиенте (у `RegisterProperty` нет вызовов, см. N8). Сетевых событий тоже нет: игровой код не вызывает `GetEvent<T>` и `Events.Send`.
- Сетевых сервисов нет: у `AddNetworkService<T>` нет вызовов, клиент не шлёт `ServiceGetOrCreate`.
- Клиент сам сущности не создаёт и не уничтожает: игровой код не вызывает `AddLocalEntity`, `INetworkEntityFactory.Send`, `INetworkEntityIds.GetEntityId`, `NetworkEntity.Destroy()`. Поэтому честный клиент не шлёт на сервер `CreateRequest`, `Destroy` и `Event`, а сервер не шлёт клиенту `DestroyUpdate`, `PropertyUpdate` и `Event`.
- Состояние матча идёт через свои команды и снапшоты GamePlay, мимо `INetworkObjectsCollection`.

## Пункты

### 1. Переполнение диапазона id (F2.19): не подтверждено

- Клиентский `NetworkEntitiesIds` (`index*10000 + counter` без проверки) — мёртвый код. `GetEntityId` вызывается только из `AddLocalEntity`, а у того нет вызовов.
- Серверный `EntityBuilder` считает id как `owner.Index * 100000 + counter`. Диапазон пользователя переполнится только на 100000 сущностях, сейчас их 1 на матч. Int переполнится при индексе пользователя >= 21475. Индекс растёт с каждым входом в сессию, но переподключения в сессию в B нет (N13). Недостижимо.
- Латентная проблема: диапазоны клиента (×10000) и сервера (×100000) не согласованы. Если клиент начнёт создавать сущности, у клиента пользователя 10 появится id 100001, а на сервере это id игрока пользователя 1. Когда клиентские сущности понадобятся, `SharedEntityIds` из A переносить целиком: и клиент, и сервер.
- Касается только злонамеренного клиента: `EntityCreateCommand` принимает от клиента любой id и любой payload и рассылает их остальным. После N9 занятый id даёт явное `InvalidOperationException`, сессия не виснет. Но клиент может до старта `GameFlow` занять id чужого игрока (`index*100000+1`), и тогда `Build` упадёт. Так можно испортить только свой матч. Проверка из A (`Forbidden` через `SessionRequestException`) опирается на `ErrorResponse` (N4). См. раздел "Для оркестратора".

### 2. Буфер создания (F2.18): не подтверждено

- Сценарий A: `PropertyUpdate` или `Event` для сущности приходят, пока `CreateRemote` ещё грузит её скоуп. Обновление при этом отбрасывается с warning, а событие падает на `Entries[id]` (`KeyNotFoundException`).
- В B у сущностей нет свойств и событий, сервер таких сообщений не шлёт. Код уязвим, но пути к багу нет.

### 3. Список уничтоженных id (F2.18): не подтверждено

- Сценарий A: `DestroyUpdate` или запоздалое сообщение приходит для уже уничтоженной сущности (`EntityDestroyedCommand` берёт `Entries[id]`).
- В B `DestroyUpdate` рассылается только в ответ на клиентский `Destroy`, а клиент его не шлёт. Когда владелец уходит, сервер шлёт `RemoteDisconnect`, клиент гасит lifetime пользователя, и сущность снимается сама. Других сообщений для этой сущности нет: нет ни свойств, ни событий.
- Есть похожий случай: соперник уходит, пока клиент ещё грузит его игрока (`CreateRemote`). Тогда `_entities.Add` и `_objects.Add` подписываются на уже завершённый lifetime. `Lifetime.Listen` пишет `LogError("Trying to listen terminated lifetime")` и сразу удаляет запись. В итоге в консоли одна строка ошибки, а матч всё равно заканчивается из-за ухода соперника. Это не гонка уничтоженных id из A, отдельно не чинил.

## Отличия от A

Фикс не перенесён. В A этот слой живой: сущности создают клиенты, у сущностей есть свойства и события (сундуки, комнаты, лифты). В B через этот слой идёт только серверная сущность игрока, и свойств у неё нет.

## Для оркестратора

- Предлагаю для N11 статус `не подтверждено`. Перенос понадобится, если игра начнёт пользоваться сетевыми свойствами, событиями или клиентскими сущностями. Тогда переносить `742f8168f` целиком: `NetworkObjectsCollection` с состояниями id и `SharedEntityIds` на клиенте и сервере.
- Злонамеренный клиент может слать `CreateRequest`, `Event` и `Destroy`, которые честный клиент B не шлёт. Варианты на решение: (а) вместе с N4 перенести из A проверку диапазона в `EntityCreateCommand` (`SharedEntityIds` + `Forbidden`); (б) пока клиентское создание сущностей не используется, запретить его на сервере. Это вопрос безопасности (рядом с S4), а не N11.
